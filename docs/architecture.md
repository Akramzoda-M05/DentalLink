# DentalLink: целевая архитектура

## Цель и границы

DentalLink — система одной стоматологической клиники с публичной записью пациентов и закрытой рабочей зоной сотрудников. Пациент не создаёт аккаунт и оформляет запись по имени и телефону. Сотрудники входят в систему и получают права по ролям `admin`, `receptionist` и `doctor`. Платёжный шлюз не входит в текущий объём.

Архитектура сохраняет описанные в техническом задании процессы, в том числе сетку расписания с шагом 30 минут, удержание слота на 10 минут, ручную запись и перенос, врачебные статусы и напоминания Telegram за 24 и 2 часа.

## Технологические решения

| Область | Решение | Причина |
|---|---|---|
| Backend runtime | .NET 10 LTS, ASP.NET Core 10 | LTS снижает частоту крупных обновлений production-среды. Патчи runtime и SDK обновляются регулярно. |
| API architecture | Domain, Application, Infrastructure, API, Shared | Зависимости направлены внутрь; домен и сценарии приложения не зависят от ASP.NET Core или PostgreSQL. |
| Use cases | CQRS с MediatR | Команды и запросы остаются отдельными сценариями с валидаторами и явными границами транзакций. Это не event sourcing. |
| Validation | FluentValidation в Application | Проверки входных команд собраны рядом со сценариями; API переводит ошибки в `ValidationProblemDetails`. |
| Persistence | EF Core 10, Npgsql 10, PostgreSQL | Реляционные ограничения и транзакции остаются авторитетной защитой целостности и расписания. Схема меняется миграциями. Часто используемые роли, специализации, статусы и типы уведомлений хранятся как BIGINT FK на справочники с уникальным `code`. |
| Staff identity | ASP.NET Core Identity | Хранение пользователей и безопасная проверка паролей поручаются проверенной платформенной реализации. Пациенты не получают Identity-аккаунты. |
| Staff session | Короткоживущий JWT access token и ротируемый refresh token | Access token используется только API; refresh token хранится в БД в виде хэша и доставляется в HttpOnly/Secure cookie. Refresh и logout защищаются от CSRF. |
| Mapping | Mapster с явной конфигурацией | Убирает повторяющееся копирование DTO, сохраняя конфигурацию отображений рядом с API-контрактами. EF-запросы проецируются в DTO на стороне SQL. |
| API errors | ASP.NET Core Problem Details и единый exception handler | Клиент получает стабильный формат ошибок без утечки stack trace, SQL и внутренних деталей. |
| Logging | Serilog с JSON-полями и correlation/trace id | Структурированные записи пригодны для поиска, корреляции запросов и вывода в контейнерный stdout. |
| Frontend | React 19, TypeScript, Vite, React Router | SPA разделяется по пользовательским функциям и загружает рабочие разделы по маршрутам. |
| Frontend data/state | TanStack Query для server state; Zustand только для локального client state | Сетевые данные кэшируются и инвалидируются по ключам запросов; глобальное дублирование server state не создаётся. |
| Frontend forms | React Hook Form + Zod | Формы имеют схему входных данных, повторно используемую для клиентской проверки. Серверная валидация остаётся обязательной. |
| UI | Tailwind CSS и shadcn/ui | Стили и доступные примитивы остаются в исходниках приложения и адаптируются к русскому, тоҷикӣ и English интерфейсам. |
| Cache and short holds | Redis | Используется для ускорения каталога и координации короткого удержания. Потеря Redis не должна нарушать целостность: подтверждение записи всегда проверяется и коммитится в PostgreSQL. |
| Notifications | Таблица outbox и hosted worker | Событие уведомления сохраняется одной транзакцией с записью; worker повторяет отправку идемпотентно и не теряет сообщение при перезапуске. |
| Deployment | Docker images, Docker Compose для разработки, CI workflow | API, SPA, PostgreSQL и Redis запускаются воспроизводимо; production secrets поступают через окружение/secret manager. |
| Tests | xUnit, FluentAssertions, ASP.NET Core integration tests; Vitest и React Testing Library | Domain/Application проверяются отдельно, а HTTP, PostgreSQL и пользовательские потоки — интеграционно. |

## Слои backend

```text
API ───────────────► Application ─────────────► Domain
 │                         ▲
 └──────► Infrastructure ──┘
Shared: только стабильные примитивы и контракты, которым действительно нужны несколько слоёв
```

- **Domain**: сущности, value objects, доменные правила статусов и инварианты. Не содержит EF Core, HTTP или Identity.
- **Application**: команды и запросы, DTO, FluentValidation, политики сценариев, интерфейсы хранилищ/часов/внешних сервисов и транзакционные границы.
- **Infrastructure**: EF Core mappings и migrations, PostgreSQL, Redis, Identity persistence, Telegram client, outbox worker, реализации application-интерфейсов.
- **API**: versioned REST endpoints, authentication/authorization, Problem Details, rate limits, health endpoints и OpenAPI.
- **Shared**: небольшой набор общих типов ошибок/результатов. Слой не превращается в свалку утилит; типы перемещаются сюда только при реальном общем использовании.

Repository Pattern не вводится поверх `DbContext` по умолчанию. Репозитории добавляются только для агрегатов, где они упрощают доменные границы и конкурентные операции бронирования.

## Слои frontend

```text
src/
  app/          providers, error boundary, route shell
  api/          Axios client, DTO schemas, shared HTTP errors
  features/     booking, catalog, staff-auth, schedule, appointments, admin
  components/   общие доступные UI-компоненты
  hooks/        общие hooks
  layouts/      public, staff
  pages/        страницы маршрутов
  routes/       route definitions and guards
  store/        только UI state без копирования TanStack Query cache
  types/        общие типы интерфейса
  utils/        форматирование, даты и локализация
  assets/       оптимизированные локальные ресурсы
```

Публичная запись и кабинет персонала имеют отдельные layouts и route guards. Lazy loading применяется на границах маршрутов; `Suspense` показывает понятное состояние загрузки, а Error Boundary — восстановимую страницу ошибки. Все элементы управления доступны с клавиатуры и имеют видимый focus.

## Ключевые границы безопасности

- Публичные endpoint’ы каталога и свободного расписания возвращают только данные, нужные для записи; контакты и заметки пациента не попадают в публичные ответы.
- Команды создания, отмены и переноса проверяют срок и допустимость операции на сервере. ID врача и пациента не считаются доверенными только потому, что они пришли от клиента.
- Просмотр/отмена пациентом требуют одноразового подтверждения через Telegram deep link/code; знание телефона само по себе не выдаёт доступ к истории визитов.
- Staff API использует JWT bearer и policy/role authorization. Разделение ролей применяется также в application-сценариях, а не только в UI.
- Refresh cookie имеет `HttpOnly`, `Secure`, ограниченный `SameSite` и отдельную защиту CSRF. Access token не сохраняется в `localStorage`.
- Вход персонала, публичное бронирование, поиск записи и выдача/обновление токенов ограничиваются rate limiter’ом. Ответы не раскрывают существование телефона/учётной записи.
- CORS разрешает только заданные origin’ы. Production ingress завершает TLS и включает HSTS/redirects; API включает HTTPS redirection только при прямом внешнем TLS endpoint. Security headers, ограничения тела и секреты вне репозитория обязательны.
- EF-запросы параметризованы; SQL строится из типизированных выражений. Для сортировки клиентские поля сопоставляются allowlist’ом.

## Целостность расписания и записи

PostgreSQL является единственным источником истины для занятости слотов. Redis lock или cache ускоряет координацию, но не заменяет SQL-транзакцию и ограничения БД. Одновременные подтверждения должны иметь ровно одного победителя при конкурентном запросе.

Продолжительность услуги кратна 30 минутам, поэтому запись на 60/90 минут занимает несколько смежных ячеек. При реализации booking-модуля модель БД должна связывать одну запись со всеми занятыми ячейками и проверять весь диапазон атомарно. Отмена освобождает ячейки, сохраняя историю талона. Перенос атомарно освобождает исходный диапазон и занимает новый.

Внешняя отправка Telegram не выполняется внутри транзакции пользовательского HTTP-запроса. Запись, её услуги, занятые ячейки и событие outbox коммитятся вместе; worker отправляет сообщение и сохраняет результат/повторную попытку.

Все времена хранятся как UTC `timestamptz`; отображение и правила рабочего календаря используют явно настроенную часовую зону клиники. Даты смен хранятся как календарные даты клиники, а не выводятся из локальной зоны сервера.

## API-контракты

- JSON REST API версионируется (`/api/v1`).
- Коллекции поддерживают лимитированную pagination; фильтры типизированы, сортировки ограничены allowlist’ом.
- Для создания брони поддерживается idempotency key, чтобы повтор HTTP-запроса не создавал повторную запись.
- Успешное создание возвращает `201 Created` и ссылку на созданный ресурс; конфликт расписания возвращает `409 Conflict`; ошибки валидации — `400` с `ValidationProblemDetails`.
- OpenAPI документируется по реальным request/response DTO, ошибкам, авторизации и ограничениям.

## Наблюдаемость и эксплуатация

- `/health/live` отвечает о живом процессе; `/health/ready` проверяет доступность PostgreSQL и обязательных зависимостей приложения.
- Логи структурированы, содержат trace id и не включают пароли, JWT, refresh token, Telegram bot token или полные медицинские заметки.
- Контейнеры запускаются не от root, используют health checks и фиксированные major/minor образов.
- Backup PostgreSQL, проверка восстановления, ротация секретов и сроки хранения логов описываются в deployment-инструкции до production-релиза.
- CI выполняет restore, build, unit/integration tests, frontend lint/typecheck/build, миграционную проверку и сборку контейнеров.

## Известное состояние исходного дерева

В текущем backend уже есть четыре проекта и начальная схема EF/SQL, но нет прикладных сценариев, завершённой authentication-схемы, миграций, outbox или API для расписания. В `frontend/dental_link` находится начальный шаблон Vite, а не DentalLink UI; этот каталог уже присутствует как незакоммиченная работа и должен быть сохранён при последующих изменениях.

Существующая SQL-модель хранит у записи только один `slot_id`, чего недостаточно для процедур длиннее одной ячейки. Это будет исправлено в миграционном этапе до реализации полноценной записи. Нельзя считать текущий seed источником production-данных.
