## 2. Реализованная архитектура проекта

### 2.1. Конфигурация и безопасность подключения (PDO)
- `config/config.example.php`: эталонный файл конфигурации, хранящийся в репозитории Git. Содержит параметры DSN: хост, порт, имя БД, логин и пустой пароль для локального сервера XAMPP.
- `config/config.php`: рабочий конфигурационный файл с реальными учётными данными, **добавлен в `.gitignore`** и не попадает в публичный репозиторий.
- `src/Core/Database.php`: реализует единое подключение PDO на весь жизненный цикл HTTP-запроса (Singleton/Static Container). Настройки PDO:
  - `PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION` — любые ошибки SQL немедленно выбрасывают `PDOException`;
  - `PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC` — все строки возвращаются как ассоциативные массивы;
  - `PDO::ATTR_EMULATE_PREPARES => false` — принудительное отключение клиентской эмуляции и выполнение подлинных серверных подготовленных запросов.

### 2.2. Обработка ошибок
В `public/index.php` зарегистрирован глобальный обработчик непойманных исключений через `set_exception_handler`. При возникновении критического сбоя пользователь получает стилизованную страницу ошибки с кодом 500. Технический стек и текст исключения выводятся **исключительно** при флаге `'debug' => true`, защищая внутреннюю структуру проекта от утечки при `'debug' => false`.

### 2.3. Слой репозиториев (`src/Repositories/`)
Весь SQL-код изолирован в классах репозиториев:
1. `DoctorRepository`:
   - `paginate(array $filters, int $page, int $perPage)`: безопасный двухэтапный запрос (SELECT COUNT(*) + SELECT ... LIMIT :limit OFFSET :offset) с явным связыванием `PDO::PARAM_INT`;
   - `buildWhere(array $filters)`: экранирование спецсимволов LIKE (`addcslashes($q, '%_\\')`), поиск по полному ФИО (`CONCAT_WS`), фильтры по `specialization_id`, `cabinet_id`, `status`, `min_experience`;
   - `create(array $data)` и `update(int $id, array $data)`: строгий белый список полей `FIELDS` и метод `onlyFields()` исключают вставку произвольных полей;
   - `delete(int $id)`: удаление записи с контролем внешних связей;
   - `emailExists(string $email, ?int $excludeId)` и `phoneExists(...)`: запросы проверки уникальности для валидатора формы;
   - `staffReport()`: отчёт с условной агрегацией `SUM(condition)` и `LEFT JOIN`.
2. `SpecializationRepository`: получение списка медицинских направлений (`all()`, `ids()`, `find($id)`).
3. `CabinetRepository`: получение перечня лечебных кабинетов и кресел (`all()`, `ids()`, `find($id)`).
4. `AppointmentRepository`: учёт записей пациентов к врачам (`countByDoctor($id)`, `allByDoctor($id)`), используемый для контроля ограничений целостности.

### 2.4. Серверная валидация (`src/Core/Validator.php`)
- Валидация цепочкой методов: `required`, `maxLength`, `email`, `date`, `in`, `pattern`, `addError`.
- Проверка реального существования календарной даты через `checkdate()`.
- Бизнес-проверки в контроллере:
  - Возраст врача не менее 21 года (`birth_date <= date('Y-m-d', strtotime('-21 years'))`);
  - Дата приёма на работу не может быть в будущем;
  - Уникальность email и номера телефона в БД клиники;
  - Проверка вхождения внешних ключей в список существующих ID через `$specializations->ids()` и `$cabinets->ids()`.
- При наличии ошибок возвращается код `422 Unprocessable Entity`, а шаблон формы `views/doctors/form.php` повторно выводит введённые значения с подсветкой классов `is-invalid` и подсказками `.invalid-feedback`.

### 2.5. Паттерн PRG (Post/Redirect/Get)
Все операции модификации (`POST /doctors/create`, `POST /doctors/{id}/edit`, `POST /doctors/{id}/delete`) после успешного выполнения завершаются отправкой HTTP-заголовка `Location` со статусом `302 Found`. Это предотвращает случайную повторную отправку формы при обновлении страницы пользователем по клавише F5.

## 3. Ответы на контрольные вопросы к защите

### Вопрос 1. Покажите на примере, как работала бы SQL-инъекция, если бы поиск был написан конкатенацией. Почему prepared statement её исключает?
**Ответ**:
Если бы поисковый запрос формировался прямой конкатенацией пользовательских данных:
```php
$sql = "SELECT * FROM doctors WHERE last_name LIKE '%" . $_GET['q'] . "%'";
```
При вводе пользователем строки `' OR 1=1 -- ` итоговый SQL-запрос превратился бы в:
```sql
SELECT * FROM doctors WHERE last_name LIKE '%' OR 1=1 -- %'
```
Так как условие `1=1` всегда истинно, а двойное тире `--` закомментировало остаток запроса, СУБД вернула бы абсолютно все записи базы данных, обойдя любые правила фильтрации или приватности.

**Почему prepared statement исключает инъекцию**:
При использовании подготовленного запроса (`$stmt = $pdo->prepare('... LIKE :q'); $stmt->execute([':q' => ...]);`) обращение происходит в две раздельные фазы:
1. Текст запроса с плейсхолдером `:q` передаётся в СУБД, где компилируется и строится дерево синтаксического разбора (AST). В этот момент структура запроса фиксируется навсегда.
2. Значение параметра передаётся отдельно в бинарном протоколе как чистые данные. СУБД воспринимает символы `'` и `--` строго как часть искомой строки, а не как SQL-операторы. Превращение пользовательских данных в исполняемый SQL-код становится невозможным.

### Вопрос 2. Зачем `charset=utf8mb4` в DSN, если база уже создана в `utf8mb4`?
**Ответ**:
Параметр `charset=utf8mb4` в строке подключения DSN задаёт кодировку **клиент-серверного канала передачи данных между интерпретатором PHP и сервером СУБД**.
Если база данных и таблицы созданы с `utf8mb4`, но в DSN кодировка соединения не указана, PHP по умолчанию установит системную кодировку клиента (например, `latin1` или `cp1251`). В результате при передаче русских символов или эмодзи драйвер СУБД попытается преобразовать их в `latin1`, что приведёт либо к замене всех символов кириллицы на знаки вопроса `????`, либо к искажению кодировки (кракозябры), а также может создать уязвимости обхода экранирования байтов.

### Вопрос 3. Почему имена столбцов в `create()` можно вставлять в строку SQL, а значения — нет?
**Ответ**:
1. **Значения** приходят из внешнего недоверенного источника (`$_POST`). Они могут содержать произвольные спецсимволы, кавычки и инъекции, поэтому должны передаваться **строго через параметры подготовленного запроса** (`execute([ ... ])`).
2. **Имена таблиц и столбцов** невозможно передать через плейсхолдеры параметров (стандарт SQL не допускает подстановку идентификаторов объектов схемы через `:placeholder`). Поэтому их подставляют в строку, но **только и исключительно из строгого белого списка констант в коде** (`DoctorRepository::FIELDS`), никогда не используя напрямую ключи массива `$_POST`. Дополнительный метод `onlyFields()` отфильтровывает входные данные, гарантируя, что злоумышленник не сможет внедрить в запрос лишние системные поля (например, `id`, `role_id` или `password_hash`).

### Вопрос 4. Рассчитайте LIMIT и OFFSET для 3-й страницы по 10 записей. Что покажет ваше приложение на `?page=-1` и `?page=abc`?
**Ответ**:
1. Формула расчёта:
   - `LIMIT = $perPage = 10`
   - `OFFSET = ($page - 1) * $perPage = (3 - 1) * 10 = 20`
   (СУБД пропускает первые 20 строк и считывает следующие 10 строк, то есть записи с 21 по 30).
2. Обработка некорректных значений в контроллере и репозитории:
   - При `?page=abc`: приведение `(int) $_GET['page']` превращает строку `'abc'` в `0`.
   - В `paginate()` вызывается нормализация:
     `$pages = max(1, (int) ceil($total / $perPage));`  
     `$page = min(max(1, $page), $pages);`
   - Если передано `$page = -1` или `$page = 0`, выражение `max(1, $page)` вернёт `1`. Приложение корректно отобразит **первую страницу** каталога без каких-либо ошибок.
   - Если передано значение больше максимального (например, `?page=99`), выражение `min(..., $pages)` ограничит его номером **последней страницы** (в нашем проекте — страница 3).

### Вопрос 5. Что такое шаблон PRG и что случится при F5 без него?
**Ответ**:
**PRG (Post/Redirect/Get)** — паттерн проектирования веб-приложений, согласно которому после успешной обработки HTTP-запроса методом `POST` сервер не генерирует HTML-страницу сразу, а отправляет HTTP-редирект (код `302 Found` или `303 See Other`) с заголовком `Location: /doctors/{id}` на страницу с методом `GET`.

**Что произойдёт при нажатии F5 без PRG**:
Если сервер ответит на запрос `POST` готовой HTML-страницей с кодом 200, то при нажатии пользователем клавиши F5 браузер выдаст предупреждающее диалоговое окно: *«Подтвердите повторную отправку формы»*. Если пользователь нажмёт «ОК», браузер повторно пошлёт весь пакет `POST`-данных, что вызовет:
- создание дублирующей записи в БД;
- повторное списание средств (в платёжных системах);
- ошибку нарушения уникальности ключа (`duplicate entry`).
Шаблон PRG полностью исключает эту проблему, так как в истории переходов браузера остаётся чистый запрос `GET`.

### Вопрос 6. Чем JOIN отличается от LEFT JOIN в `staffReport()`? Почему условие `status <> 'dismissed'` стоит в ON? Зачем нужны транзакции и где они понадобятся в вашем проекте?
**Ответ**:
1. **JOIN (INNER JOIN) против LEFT JOIN**:
   - `INNER JOIN` оставляет в итоговой выборке только те строки, для которых есть соответствие в обеих таблицах. Если бы в отчёте использовался `INNER JOIN`, то специализации, по которым временно нет ни одного врача (или все врачи уволены), просто исчезли бы из отчёта.
   - `LEFT JOIN` гарантирует вывод **всех специализаций из левой таблицы**, даже если к ним не привязан ни один специалист (в таком случае поля правой таблицы заполняются `NULL`, а `COUNT(d.id)` возвращает `0`).
2. **Почему условие `status <> 'dismissed'` стоит в секции `ON`, а не в `WHERE`**:
   - Секция `ON` фильтрует строки правой таблицы **до** объединения. Специализация остаётся в отчёте с нулём врачей.
   - Если вынести это условие в `WHERE (d.status <> 'dismissed')`, то для специализаций без врачей поле `d.status` будет `NULL`. Проверка `NULL <> 'dismissed'` вернёт `UNKNOWN` (ложь), и вся строка специализации будет отброшена из результата, что превратило бы `LEFT JOIN` в `INNER JOIN`.
3. **Зачем нужны транзакции и где они понадобятся в проекте DentalLink**:
   - Транзакции гарантируют свойства ACID (атомарность, согласованность, изолированность, надёжность) при выполнении группы взаимосвязанных SQL-запросов по принципу «всё или ничего» (`beginTransaction()`, `commit()`, `rollBack()`).
   - В DentalLink транзакции критически необходимы в следующих сценариях:
     - **Онлайн-запись пациента на приём**: создание записи в `appointments`, одновременное переключение статуса тайм-слота в `time_slots` на `booked`, привязка выбранных услуг в `appointment_services` и постановка в очередь уведомления в `notifications`. Если на любом из этапов произойдёт сбой, транзакция откатит изменения, предотвратив бронирование слота без создания самого приёма.
     - **Отмена приёма**: перевод статуса записи в `cancelled` и синхронное освобождение тайм-слота со сменой статуса на `free`.
