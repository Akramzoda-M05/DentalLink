# План реализации DentalLink

Этапы выполняются последовательно. Каждый этап завершается документацией, сборкой, проверками безопасности и релевантными тестами; следующий этап не должен оставлять предыдущий в неработающем состоянии.

## Этап 0. Архитектура и аудит

- Зафиксировать границы домена, стек, слои, ключевые решения безопасности и согласованность расписания.
- Уточнить исходное состояние репозитория и сохранить уже существующие незакоммиченные файлы.
- Результат: `docs/architecture.md` и этот план.

## Этап 1. Рабочая основа и CI

- Выстроить solution projects и направление ссылок Clean Architecture; добавить только необходимые Shared-типы.
- Централизовать версии NuGet, конфигурацию окружений, секреты и API startup.
- Добавить единое Problem Details/exception handling, health checks, CORS, rate limiting, security headers и OpenAPI.
- Настроить backend unit/integration test projects, frontend lint/typecheck/test/build и CI workflow.
- Добавить Dockerfile API/UI и compose для локальной разработки с PostgreSQL и Redis.
- Результат: все сервисы запускаются локально; health endpoints и CI проходят.

## Этап 2. Domain, схема и миграции

- Разделить текущие большие файлы сущностей/enum по доменным понятиям.
- Уточнить агрегаты расписания, услуг, пациентов, записей и уведомлений.
- Смоделировать запись, занимающую несколько 30-минутных ячеек; обеспечить атомарный захват диапазона, повторное использование отменённых ячеек и защиту от конфликтов врача/кабинета.
- Добавить Identity/refresh-token/outbox persistence и начальную EF migration; проверить миграцию на чистой PostgreSQL.
- Сохранить только безопасный синтетический seed для локальной разработки.
- Результат: миграции создают целостную схему с уникальными/check/exclusion constraints и индексами.

## Этап 3. Staff authentication и authorization

- Identity для персонала, роли и policies для admin/receptionist/doctor.
- Login, короткий JWT, хэшированный refresh token с rotation/revocation, CSRF-защита cookie endpoint’ов, rate limiting и аудит.
- Тесты проверки пароля, ролей, истечения, повторного использования refresh token и запрещённых действий.
- Результат: безопасный завершённый staff authentication flow и OpenAPI.

## Этап 4. Публичный каталог и бронирование

- Каталог врачей/услуг и фильтрация; свободные слоты с учётом длительности и диапазона процедуры.
- Временное удержание 10 минут, атомарное создание записи, idempotency и обработка конкурентных запросов.
- Повторный поиск и отмена записи с нераскрывающими ответами и лимитированием.
- Результат: интеграционные тесты PostgreSQL для одновременной брони, истечения hold, отмены и повторного использования диапазона.

## Этап 5. Рабочие процессы персонала

- Timeline расписания, ручное создание/перенос/отмена, график смен, назначение кабинета и процедур.
- Персональный график врача, допустимые переходы статусов визита и врачебные заметки с ограничением доступа.
- Справочники услуг, цен, длительностей и профилей врачей.
- Pagination, filtering, sorting, audit trail.
- Результат: политики доступа и бизнес-переходы покрыты тестами.

## Этап 6. Telegram reminders и background jobs

- Transactional outbox, worker с retry/backoff и идемпотентностью.
- Подтверждение, напоминания за 24/2 часа, отмена; обновление Telegram chat binding.
- Мониторинг очереди, dead-letter/retry и управляемый shutdown.
- Результат: тесты повторной отправки, временных окон, отменённых/перенесённых визитов и ошибок Telegram.

## Этап 7. React SPA

- Пересобрать шаблон `frontend/dental_link` под feature-based структуру, сохранив текущие пользовательские файлы до осмотра их авторства/назначения.
- Публичный каталог, выбор врача/услуги, календарь, hold, оформление записи и экран результата.
- Закрытая staff-зона: login, layouts и guards, расписание, Timeline, карточка визита, администрирование.
- Axios client, TanStack Query, Zustand для локального UI state, React Hook Form/Zod, адаптивность, локализация ru/tg/en, доступность.
- Error Boundaries, route-level lazy loading, тесты Vitest/Testing Library и проверка bundle.
- Результат: законченные пользовательские потоки на desktop/mobile с обработкой загрузки, пустого состояния и ошибок.

## Этап 8. Production readiness

- CI/CD, immutable images, environments, secret management, HTTPS/reverse proxy, health/readiness, backups и восстановление.
- Нагрузочные тесты ключевого бронирования, анализ slow SQL, индексов, логов и метрик.
- Руководства по rollout/rollback, миграциям, эксплуатации Telegram, ротации секретов и аварийному восстановлению.
- Результат: зафиксированный релизный checklist и проверенная процедура развертывания.

## Решения, требующие уточнения до соответствующего этапа

1. Канал подтверждения пациентского доступа согласован: Telegram deep link/code. Код должен быть одноразовым, ограниченным по времени и привязанным к конкретной попытке доступа; номер телефона сам по себе не выдаёт медицинскую информацию. Пароль/постоянный аккаунт пациента не вводится.
2. Клиника работает по местному календарю, а инфраструктура — в UTC. До реализации смен нужно подтвердить IANA/Windows timezone клиники и правило обработки изменения часового пояса.
3. Нужны реальные параметры для production: разрешённые origin’ы, домен, Telegram bot secret/chat-link flow, SMTP/SMS провайдер и требования хранения/удаления персональных и медицинских данных. Секреты в Git не добавляются.
